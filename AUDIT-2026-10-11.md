## F1. P1: Rejected commits still release Welcomes and advance state

Locations:

- `example-realistic-demo/client/approvals.ts`, lines 163-182.
- `example-realistic-demo/room-logic.ts`, lines 342 and 396-406.
- `example-realistic-demo/index.ts`, lines 576-580.

The client treats successful socket submission as successful server
acceptance. At `approvals.ts:163-170`:

```ts
        const delivered =
            send({ type: 'mls', kind: 'commit', payload: added.commit }) &&
            send({
                type: 'welcome',
                to: request.identity,
                payload: added.welcome
            }) &&
            send({ type: 'approve', identity: request.identity })
```

It then executes `state.group.value = added.newState` at line 180.
Meanwhile, the server enforces `MLS_WRITE_INTERVAL_MS = 50` and rejects
too-rapid writes before assigning a log sequence number. Socket submission
does not communicate that rejection back to this operation.

Two serialized approvals can finish inside that interval. The second
commit is discarded, but its Welcome and approval are still submitted.
The creator and second joiner reach epoch 2 while the first joiner remains
at epoch 1. Replay cannot supply a commit absent from the server log.
The same missing acceptance boundary also matters for full-log rejection.

Reproduction: initialize the real demo ciphersuite and users; run two
production approval operations consecutively; have the send callback apply
the production `classifyMlsWrite`; deliver accepted commits and Welcomes;
then send a creator application message to both joiners.

Command executed from the review checkout, exit 0:

```sh
node /private/tmp/demo-throttle-probe.cjs
```

Observed output, with the long error omitted here:

```text
MLS epoch 0 gap null verdict ok
MLS epoch 1 gap 4 verdict rate-limited
accepted commits 1 sent welcomes 2 creator epoch 2
status Let charlie in.
bob epoch 1 charlie epoch 2
charlie result applicationMessage
ok 1 - rapid approvals produce a permanently missing epoch
```

Bob's actual rejection was:
`ValidationError: Cannot process message, epoch is in the future`.

Recommendation: correlate each pending commit with server acceptance.
Release its Welcome, ledger update, and local epoch transition only after
acceptance. Preserve pending state for retries and surface rejection to the
operation. A fixed delay alone cannot handle capacity errors or lost writes.

## F2. P2: A normal commit can reactivate a group awaiting ReInit

Locations: `src/process-messages.ts`, lines 107-113, 125, and 458-475.

The inbound guard checks only removal:

```ts
    if (state.groupActiveState.kind === 'removedFromGroup') {
```

For a subsequent ordinary commit, the state calculation at lines 458-462
falls through to:

```ts
            : { kind: 'active' }
```

A group member can send validly authenticated traffic after the ReInit
commit. An honest receiver in `suspendedPendingReinit` accepts it. A normal
commit then changes the receiver to `active`, discarding its pending ReInit
state and enabling its normal sending API again.

This requires an existing member with the old group's keys. It is not an
unauthenticated outsider attack. The reproduction modifies only the
sender's local suspension flag to emulate a nonconforming member; the
receiver's state remains untouched and uses the public receive APIs.

RFC 9420 section 12.4.2 requires a client that has processed ReInit to cease
sending on the old group and await the matching Welcome. Accepting a later
commit must not silently remove that restriction. See
[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4.2).

Reproduction: create a two-member group, commit ReInit, let Bob process it,
then have Alice send an application message and a normal commit using the
post-ReInit keys. Finally call Bob's normal application-send API.

Command executed from the review checkout, exit 0:

```sh
node /private/tmp/mls-suspended-probe.cjs
```

Exact output:

```text
bob after ReInit: suspendedPendingReinit
post-ReInit application: applicationMessage
bob after post-ReInit commit: active
honest receiver can send after revival: true
```

Recommendation: preserve suspension across receive operations and reject
new state-changing traffic on a suspended group. Define any intended
historical-message behavior separately. Test that authenticated subsequent
commits cannot restore sending or erase the expected ReInit parameters.

## F3. P2: Public removal exposes the supposedly private creator name

Locations:

- `example-realistic-demo/client/mls-actions.ts`, lines 297-305.
- `example-realistic-demo/client/views/explainer.ts`, lines 93-99.

Removal commits explicitly use this setting at `mls-actions.ts:303`:

```ts
            wireAsPublicMessage: true,
```

A removal includes an update path whose leaf contains the committer's
basic credential. When the creator removes a member, the public encoded
message contains the creator's literal name. The delivery service can read
it without group keys.

The explainer promises the opposite. Lines 98-99 say:

```text
                    inside an encrypted Welcome, and the server never
                    sees it.
```

Reproduction: create a group under the name `PRIVATE-CREATOR-NAME`, add
Bob, then remove him through the real `commitRemove`. Decode only base64
and the public MLS envelope and search its bytes for that name.

Command executed from the review checkout, exit 0:

```sh
node /private/tmp/demo-name-probe.cjs
```

Exact output:

```text
add wireformat mls_public_message creator name in public bytes false
remove wireformat mls_public_message creator name in public bytes true
ok 1 - public removal exposes creator name without any keys
```

Recommendation: use private removal commits if this confidentiality promise
is intended. Otherwise, correct the disclosure and corresponding comments
to explain that later public commits can expose the creator's name.

## F4. P2: Cancellation can miss a fully derived attachment schedule

Locations: `src/attachment/reader.ts`, lines 352-366 and 478-489.

The sequential reader assigns its state after an asynchronous derivation:

```ts
                state = await openCommitment(
                    cek, ref.objectId,
                    head.subarray(0, 32), head.subarray(32, prefixSize),
                    crypto,
                )
```

Cancellation during that await sees a null state. The wipe function only
wipes an existing state, at lines 364-366:

```ts
        if (!stateWiped && state) {
            stateWiped = true
            wipeSealState(state)
```

The existing cleanup expects later startup work to fail and enter its
catch. That is not guaranteed. If the first input chunk contains the whole
object and cancellation occurs after the final KDF computation but before
its promise returns, startup can finish using buffered bytes. The cancelled
output stream never pulls, and the late-assigned schedule is not wiped.

Reproduction uses real AES128-GCM/SHA256 operations. A wrapper pauses the
return of the computed `nonce_base` result, cancels the output reader, then
releases the result and waits for metadata verification to finish. No
cryptographic error is injected in this case. The probe retains references
to allocated buffers solely to inspect whether cleanup overwrote them.

Command executed from the review checkout, exit 0:

```sh
node /private/tmp/attachment-audit-probe.mjs
```

Exact cancellation output:

```text
cancel while schedule pending, full ciphertext buffered: CEK wiped
cancel race: payload_key remains nonzero after start finishes
cancel race: acc_key remains nonzero after start finishes
cancel race: nonce_base remains nonzero after start finishes
PASS: consumer cancellation retains all derived schedule secrets
```

Impact: cancellation fails the explicit key-overwrite contract for the
payload key, snapshot key, and nonce base. This demonstrates unwiped memory,
not exfiltration or a remote memory-reading primitive.

Recommendation: latch cancellation and check it immediately after awaited
state acquisition. Wipe the acquired state before returning. Add a
regression with a fully buffered object and a delayed final derivation.

## F5. P2: CommonJS imports produce inconsistent error-class identities

Location: `package.json`, lines 12-24 and 45-46.

The CommonJS build changes output filenames to `.cjs` but leaves internal
module specifiers pointing to `.js`. A successful `npm run build` produces
this line at `dist/authentication-service.cjs:25`:

```js
var import_mls_error = require("./mls-error.js");
```

On the tested Node version, the root CommonJS entry consequently uses the
ESM error class, while the explicit CommonJS `mls-error` subpath exports a
separately evaluated class. An actual library exception fails `instanceof`
against that documented subpath class. This matters especially for error
types available through subpaths rather than the root export.

Reproduction after `npm run build`, executed in the review checkout:

```js
const m = require('@vanishing.page/webcrypto-mls');
const errors = require('@vanishing.page/webcrypto-mls/mls-error');
m.failClosedAuthenticationService.validateCredential(
  { credentialType: 'basic', identity: new Uint8Array() },
  new Uint8Array()
).catch(error => {
  console.log('error name:', error.constructor.name);
  console.log('instanceof root UsageError:', error instanceof m.UsageError);
  console.log('instanceof subpath UsageError:',
    error instanceof errors.UsageError);
});
```

Executed with `node --input-type=commonjs`, exit 0. Exact observed output:

```text
error name: UsageError
instanceof root UsageError: true
instanceof subpath UsageError: false
```

Recommendation: make the CommonJS graph resolve to one consistent set of
CommonJS modules, including internal extensions. Test error identity using
the package's exported root and subpaths, rather than source imports.

## F6. P2: Nested CommonJS subpaths have no declared types

Locations: `scripts/cts.mjs`, lines 11-13; `package.json`, lines 22-24.

The export map promises `./dist/*.d.cts` for CommonJS subpaths. The copy
script only reads the top-level directory:

```js
const files = readdirSync(distDir).filter(f => f.endsWith('.d.ts'))
```

It never visits `attachment/`, `crypto/`, or other nested directories.
After the successful build, a filesystem probe reported:

```text
dist/attachment/reader.d.cts false
dist/crypto/ciphersuite.d.cts false
```

A separate temporary consumer linked the built package under its normal
package name and contained:

```ts
import { decryptAttachmentStream } from
  '@vanishing.page/webcrypto-mls/attachment/reader';
console.log(decryptAttachmentStream);
```

Compilation with the installed TypeScript compiler and these options
exited 2:

```text
--noEmit --strict --skipLibCheck --module NodeNext --target ES2022
```

The actual diagnostic included this exact excerpt:

```text
error TS7016: Could not find a declaration file for module
```

It identified `@vanishing.page/webcrypto-mls/attachment/reader` and the
resolved `dist/attachment/reader.cjs`, which implicitly had type `any`.

Recommendation: generate CommonJS declarations recursively and verify
their internal module references. Add external consumer compilation for
both a nested attachment subpath and a nested crypto subpath.

## F7. P3: Derivation failures bypass schedule cleanup

Locations: `src/attachment/schedule.ts`, lines 129-138;
`src/attachment/reader.ts`, lines 142-146.

Schedule construction derives secret buffers sequentially without cleanup
if a later derivation rejects. For example:

```ts
    const payloadKey = await sealKdf(
        kdf, pid, 'payload_key', [cek], rawFields, crypto.keyLength,
    )
    const snapKey = await sealKdf(
        kdf, pid, 'acc_key', [cek], rawFields, nh,
    )
```

Separately, `verifyRoot` obtains ownership of a complete schedule and then
awaits another operation before transferring ownership:

```ts
    const state = await openCommitment(
        cek, objectId, prefix.salt, prefix.storedCommitment, crypto,
    )
    await checkRoot(state, prefix, refSnapshot)
    return state
```

If the root KDF rejects, comparison-failure cleanup does not run, and the
range caller has not yet received the state to wipe it.

Reproduction wraps the real KDF and injects failures at `nonce_base` and
`snap_epoch_root`. The attachment probe above exited 0 with:

```text
partial schedule: payload_key remains nonzero after rejection
partial schedule: acc_key remains nonzero after rejection
range root failure: owned CEK wiped
range root failure: payload_key remains nonzero after rejection
range root failure: acc_key remains nonzero after rejection
range root failure: nonce_base remains nonzero after rejection
PASS: both exception-path retention defects reproduced
```

No remote trigger or plaintext disclosure was established. This finding
concerns provider-failure cleanup, unlike F4's normal cancellation race.

Recommendation: wipe successfully derived buffers when construction fails,
and wipe the acquired state if `checkRoot` rejects before ownership passes
to the caller. Keep caller-owned input buffers untouched.
