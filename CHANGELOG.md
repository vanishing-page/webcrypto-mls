## Unreleased

This release is the result of a security audit of the whole library and
its demos (`security-audit.md`, with a finding-to-commit map in its
"Resolution status" section). Everything below comes from that work.

Read the "Breaking" items before upgrading: several of them make the
library reject messages it used to accept, so a peer that does not follow
RFC 9420 closely may stop interoperating.

### Changed

- **Breaking:** `defaultAuthenticationService` is gone. It accepted every
  credential unconditionally and was the default for `createGroup`,
  `joinGroup`, and `joinGroupExternal`, so an application that never
  configured one silently authenticated nobody. It is replaced by two
  explicitly named exports: `failClosedAuthenticationService`, which
  `defaultClientConfig` now carries and which throws a `UsageError` the
  first time a credential decision is needed, and
  `unsafeAcceptAllAuthenticationService`, the old accept-all behavior,
  which a caller now has to name. Applications that relied on the old
  default must pass `{ ...defaultClientConfig, authService }` to
  `createGroup`/`joinGroup`/`joinGroupExternal` with a real
  implementation -- or, for local testing only,
  `unsafeAcceptAllAuthenticationService`. `defaultClientConfig` is now
  exported from the package root.
- The resumption helpers (`reinitCreateNewGroup`, `branchGroup`,
  `joinGroupFromBranch`, `joinGroupFromReinit`) now carry the old group's
  `clientConfig` into the resumed group instead of resetting it to the
  library defaults.
- **Behavior change:** `defaultLifetimeConfig.validateLifetimeOnReceive`
  now defaults to `true`. A KeyPackage leaf node received from a peer has
  its `notBefore`/`notAfter` window and its total span checked against the
  local clock, so an expired or improbably long-lived KeyPackage is
  rejected instead of accepted. Clients that relied on the old permissive
  default -- or that cannot trust the local clock -- must now pass
  `lifetimeConfig: { ...defaultLifetimeConfig, validateLifetimeOnReceive:
  false }` in their `ClientConfig` to opt out.
- `AuthenticationService.validateCredential` takes a third argument,
  `priorCredential?:Credential` -- the credential currently at the leaf
  being replaced by an Update proposal or a commit's `UpdatePath`, and
  `undefined` when nothing is being replaced. Existing two-parameter
  implementations keep compiling and behave as before; enforcing identity
  continuity now requires reading the new argument. See "Security
  Considerations" in the README.
- **Breaking:** `retainKeysForGenerations: 0` now retains nothing. It
  previously retained every skipped generation forever, because
  `slice(-0)` is `slice(0)`. A client that set `0` expecting the
  strongest forward secrecy was getting the weakest; a client that set
  `0` and relied on out-of-order messages still decrypting has to name a
  real generation count now.
- **Breaking:** removing the sole remaining leaf of a group throws a
  `ValidationError` rather than an `InternalError`. The condition is
  reachable from a peer's message (a resync external join into a
  single-member group), so it is a rejected message, not a library bug.
  Code that caught `InternalError` here has to catch `ValidationError`.
- **Breaking:** `decodeReuseGuard` returns `undefined` for a buffer with
  fewer than four bytes left instead of a short value branded as a
  four-byte `ReuseGuard`. Callers already treat `undefined` as a decode
  failure.

### Security

Validation the library now performs that it did not before. Each of
these rejects input that used to be accepted.

- **Breaking:** a path secret received in an `UpdatePath` or a `Welcome`
  must derive to the public key advertised for each node on the path (RFC
  9420 7.5 and 12.4.3.1). Without the check a committer could advertise
  keys it controls while sending a path secret deriving to something
  else, splitting the group with a valid-looking commit.
- **Breaking:** a new or rotated leaf's `encryption_key` must differ from
  every key in the tree, parent nodes included, and multiple Adds in one
  commit are now validated against the tree as it accumulates rather than
  only against the pre-commit tree. Both were already enforced at join
  time, so a commit could previously build a tree this library itself
  refused to join.
- **Breaking:** a new leaf must list every credential type already in use
  in the group in its capabilities (RFC 9420 7.3). Only the converse
  direction was checked, which let a joining or rotating member lower the
  group's credential floor.
- **Breaking:** `joinGroup` and `joinGroupExternal` validate the
  `external_senders` GroupContext extension of the group they are joining
  against the caller's `AuthenticationService`, so a joiner does not
  inherit an external signer it would have refused.
- **Breaking:** `joinGroup` checks that the GroupInfo's protocol version
  matches the KeyPackage's. Only the ciphersuite was compared.
- **Breaking:** once a commit removes this client, `processMessage`
  refuses all further inbound traffic for that state. The state stays
  frozen at the removal epoch, so it used to accept a fork built from
  that epoch and an endless replay of the removing commit.
- **Breaking:** a commit whose only proposals are custom (numeric)
  proposal types requires an `UpdatePath`. Custom types are not among RFC
  9420 12.4's exceptions, so such a commit previously skipped the key
  rotation that provides post-compromise security.
- `validateUnmergedLeaves` now constrains only the non-blank nodes
  strictly between the unmerged leaf and the parent under inspection (RFC
  9420 7.9). The previous whole-direct-path rule rejected valid trees,
  which permanently blocked every join to an affected group. This one
  accepts more than before, not less.

### Fixed

- A ratchet operation no longer zeroizes secrets belonging to the
  `ClientState` the caller passed in. `ClientState` is functional and
  node objects are shared across state versions, so the in-place `fill(0)`
  left a still-held prior state deriving its AEAD key from an all-zero
  secret -- plaintext recoverable by anyone who noticed. Zeroization now
  wipes only buffers the call itself allocated.
- Content and sender-data AEAD keys and nonces are wiped in a `finally`,
  so they are cleared when the AEAD throws (a forged or corrupt message)
  and not only on the success path.
- The `Welcome` path derives its private key path along the committer's
  filtered direct path, the same walk the commit path uses. Walking to
  the geometric root could fold in a node the commit never rotated, or
  store a key against a blank node index.

### Demo (`example-realistic-demo`, `example`)

Not part of the published package, but worth reading if you have forked
either demo.

- A malformed `commit`-kind log entry no longer wedges the room: entries
  that fail to decode are skipped with a status line and the cursor
  advances. A commit that decodes and then fails to process still stops
  the queue, which is the desync that behavior exists to catch.
- Join requests are capped (64 pending identities per room), bounded (16
  KiB per key package) and rate-limited (one per second per socket), each
  with its own refusal reason.
- Every client-supplied wire string is length-bounded, and an oversized
  frame is refused before `JSON.parse`.
- Every Worker response, API and static asset alike, carries a
  `default-src 'none'` Content-Security-Policy naming the exact socket
  origin, plus `X-Frame-Options: DENY` and
  `X-Content-Type-Options: nosniff`.
- Both demos assign `window.state` only behind `import.meta.env.DEV`, so
  no build puts live group secrets in global scope. The previous gate
  also accepted any non-`production` mode, and the deployed build runs
  `--mode staging`.

### Repo

- `package-lock.json` is committed, so dev installs are pinned and
  `npm audit` is reproducible. CI installs with `npm ci`.
- `.gitignore` covers `.env.*` and common private-key file patterns, not
  just a literal `.env`.
