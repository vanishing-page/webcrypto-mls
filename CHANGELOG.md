## Unreleased

### Added

- `listPendingProposals` and `discardPendingProposal` list the pending
  proposals of a `ClientState` (reference, proposal, sender) and return
  a new state without one, so an application can unblock a group
  wedged on a proposal nobody will commit (audit 2026-09 H3).
- `ClientConfig.maxPendingProposals` (default
  `defaultMaxPendingProposals`, 256) caps the pending set. A proposal
  arriving at the cap is a `ValidationError`; nothing pending is
  evicted. A `ClientConfig` built without spreading
  `defaultClientConfig` must now supply the field.

- `processMessage` reports the authenticated sender. The
  `applicationMessage` result gains `sender` (`{ senderType, leafIndex }`)
  and `authenticatedData`; the `newState` result for an accepted commit
  gains `committer` in the same shape, `new_member_commit` with the
  joiner's leaf for an external commit. The new type is exported as
  `AuthenticatedSender`. Both changes are additive.

### Breaking

- Peer inputs now surface as the documented error classes (audit
  2026-09 L1, L8). A `ratchet_tree` extension that is empty or ends in
  a blank node is a `CodecError` from `joinGroup` and
  `joinGroupExternal`, not an `InternalError`. An unknown or GREASE
  credential type fails the decode instead of throwing `TypeError`. A
  PublicMessage carrying application content is a `ValidationError`,
  not a `UsageError`. A wrong-length Ed25519 signature key is a
  `ValidationError` under the default provider, not a `DOMException`.
  An AEAD failure inside HPKE open (a tampered Welcome, for example) is
  a `CryptoVerificationError`, not a `CryptoError`; code that caught
  `CryptoError` for that case must catch the new class.

- LeafNode and KeyPackage validation now reject an Ed25519 or Ed448
  signature key that is the identity point or of small order, with
  `ValidationError`. Such a key lets `R = identity, S = 0` verify for
  every message. The check runs before the signature check, so a leaf
  that used to fail as `CryptoVerificationError` for this reason now
  fails as `ValidationError`.

- The noble provider verifies Ed25519 and Ed448 strictly
  (`zip215: false`), matching WebCrypto's RFC 8032 behavior. A
  signature with a non-canonical `R` that noble used to accept is now
  refused, so a group mixing the two providers can no longer fork on
  it. Both providers' `verify` also return `false` for a small-order
  public key.

- `joinGroupFromBranch` (and `joinGroup` with a branch resumption PSK)
  now enforces RFC 9420 section 11.3: the branch Welcome must use the
  resuming group's version and ciphersuite, carry exactly one
  resumption PSK, and every member of the new group must match a
  member of the old one. A member matches under the new optional
  `KeyPackageEqualityConfig.compareLeafNodes`, which falls back to
  signature-key equality -- so under the default config a member must
  keep its signature key across the branch. Any failure is a
  `ValidationError`.

- `KeySchedule` no longer has an `encryptionSecret` field, so
  `ClientState.keySchedule` no longer carries it for the epoch. Anyone
  holding that secret could regenerate the whole secret tree, including
  every consumed generation (audit 2026-09 H2). The key-schedule
  derivation now returns it beside the `KeySchedule` (see
  `DerivedKeySchedule`, `EpochSecrets.encryptionSecret`), and the
  library zeroes it once the secret tree is built.

- `GenerationSecret.unusedGenerations`, part of the exported
  `ClientState` secret tree, is now a map of `{key, nonce}` pairs
  (`GenerationKeyNonce`) instead of a map of chain secrets. A skipped
  generation's chain secret derives every later generation, so a state
  compromise after one lost message recovered the whole epoch; RFC 9420
  section 9.2 allows only the key and nonce to be kept. The library has
  no serialization format, so there is no migration: state saved by an
  application in the old shape cannot be loaded. The demos' shared
  IndexedDB store moves to version 2 and discards old sessions.
  `ratchetUntil` now takes a `CiphersuiteImpl` instead of a `Kdf`.

- The default incoming-message callback, used by `processMessage`,
  `processPublicMessage` and `processPrivateMessage` when none is
  passed, is now `defaultIncomingMessageCallback` rather than
  `acceptAll`. It rejects a `new_member_proposal` (a self-signed Add
  anyone can send) and accepts everything else. Pass `acceptAll` to
  keep open self-add. `processMessage`'s callback argument may now be
  `undefined`.

- `ProposalWithSender` gains a `senderType` field (`member`,
  `external`, `new_member_proposal` or `new_member_commit`), for both
  the `proposal` and `commit` callback inputs. `addUnappliedProposal`
  takes the sender type as a new required argument.

- A received proposal that can never be committed in the current epoch
  is now rejected by `processMessage` with `ValidationError` instead of
  being stored. That covers a Remove naming a blank or out-of-range
  leaf, an Add whose KeyPackage fails validation, an ExternalInit from
  any sender, and an Update whose leaf fails leaf validation. Such a
  proposal used to be stored and then make every later `createCommit`
  throw, wedging the group. A KeyPackage or leaf signature that does
  not verify is reported as `ValidationError` here rather than
  `CryptoVerificationError`, because the message carrying it did
  authenticate. `createProposal` applies the same checks before
  signing, so it now throws where it used to store the proposal
  locally.

- KeyPackage validation now requires the `initKey` to import as a
  public key under the group's ciphersuite. A KeyPackage failing this
  used to be accepted and then make the committer's Welcome
  construction throw.

- `AttachmentRangeRead.close` is now required rather than `close?:`.
  Every range read has always returned one, and the JSDoc already told
  callers not to guard on it, so no runtime behavior changes. Code that
  wrote `read.close?.()` can drop the `?.`; code that implements the
  interface itself must now supply a `close`.

- `encryptAttachmentForGroup` no longer accepts `opts.salt`. The salt
  always comes from `crypto.rng`. `payloadKey`, `snapKey` and
  `nonceBase` derive from `(cek, salt)` alone, so a pinned salt on a
  reused CEK repeats the AES-GCM key and nonce for every segment and
  the two ciphertexts XOR to the two plaintexts. `sealObject` and
  `encryptAttachment` keep the option, now documented as test and
  vector use only. The attachment API is unreleased, so there is no
  deprecation cycle.

- `sealObject`, `openObject` and `encryptAttachment` now reject a CEK
  that is not exactly `CEK_LENGTH` (32) octets. `attachmentCek` has
  always produced 32, so the `...ForGroup` wrappers are unaffected; a
  caller supplying its own short key used to get silently weaker
  derivation and now gets `AttachmentError`.

- `validateAttachmentRef` now rejects a `snapshot` whose length is not
  one of the three KDF output sizes, or, when the KDF size is passed,
  is not exactly that. Such a ref already failed to decrypt, because
  `constantTimeEqual` rejects unequal lengths, so the change moves the
  same `AttachmentError` earlier rather than introducing one.

- `joinGroup` now throws `ValidationError`, not `UsageError`, when the
  GroupContext carries an extension the joiner's KeyPackage does not
  support. The committer caused it, so it is a peer-triggered
  rejection like every other one.

### Fixed

- `createCommit` filters the pending proposals it bundles, per RFC 9420
  section 12.2 (audit 2026-09 H3). A pending proposal is left out when
  it is invalid once the earlier kept proposals apply, when it is a
  second Remove of a leaf, an Update from a leaf being removed or from
  the committer, or a duplicate of a kept proposal. Two members
  concurrently proposing to remove the same leaf no longer wedge the
  group. Proposals passed as `extraProposals` are not filtered; an
  invalid one still rejects the call.

- Processing or creating a commit no longer alters the `ClientState`
  passed in, whether it succeeds or fails (audit 2026-09 H1). Merging
  and pruning the private key path used to zeroize the superseded HPKE
  path keys, which belong to that input state, and the receive path did
  so before checking the confirmation tag. One commit with a bad
  confirmation tag therefore left the receiver unable to decrypt the
  next honest commit, and a committer that lost a commit race, or whose
  `createCommit` threw, could not process the winner from its prior
  state. Superseded path keys are now dropped for the garbage collector
  instead, the receive path builds the new private path only after the
  confirmation tag verifies, and `createCommit` builds it only after the
  Welcome.

- Commits that every member accepted but no later joiner could join,
  or that admitted a member unable to support the group, are now
  rejected with `ValidationError`: two Updates in one commit sharing
  an encryption key or together breaking the pairwise credential rule
  (each Update is now validated against the tree as updated by the
  ones before it), an Update that keeps the sender's current
  encryption key, a committer leaf key that equals a key on its own
  UpdatePath, and an Add that does not support the extensions a
  GroupContextExtensions proposal in the same commit introduces.
