# Security audit, 2026-10-24

Audited revision: `b79561b27e9cc86adfacfab8749b69d90ee89e4c`.

Three security issues were reproduced against the library. All are rated
medium: exploitation requires an authenticated peer, an admitted
KeyPackage, or a Welcome signer accepted by the application's
AuthenticationService. No signature forgery or plaintext recovery from
ciphertext was demonstrated.

## Scope and method

Manual review focused on message authentication, proposal validation,
Welcome and resumption processing, tree updates, secret ownership,
attachment verification and cancellation, and the realistic demo's
authorization and delivery paths. Build configuration, dependency
advisories, secret-file exclusions, and production debug exposure were
also checked. Earlier audit reports were used as context, not as evidence
that a finding remains open.

The attached proof uses the default ciphersuite, real WebCrypto/HPKE,
and the repository's `testClientConfig`. That fixture accepts test
credentials. It does not model a bypass of a real AuthenticationService:
the attacker prerequisites below still apply. Every reproduction passes
on the audited code and asserts the vulnerable behavior. No library or
demo implementation was changed.

## F1. Medium: resumption APIs accept a Welcome with no resumption PSK

Locations:

- `src/resumption.ts:164`: `joinGroupFromBranch`.
- `src/resumption.ts:186`: `joinGroupFromReinit`.
- `src/client-state.ts:1130`: conditional resumption checks in `joinGroup`.

Both specialized join APIs delegate to `joinGroup`, passing the prior
state. Neither requires the received Welcome to contain a resumption PSK
of the expected usage. `joinGroup` performs its continuity checks only
inside a loop over the resumption PSKs the Welcome actually contains.
With none present, the loop does nothing. The branch membership check
at `src/client-state.ts:1240` is conditional on the same input.

An ordinary, correctly signed Welcome therefore passes either wrapper.
For ReInit, this skips the agreed new group ID and extension checks. For
branching, it skips the old-group membership restriction and proof of
possession of the old group's resumption secret. The returning state is
active, and a successful join consumes the supplied init private key.

**Reproduction:** Alice and Bob form `original`. Alice separately creates
`unrelated` and issues an ordinary Welcome to a fresh Bob KeyPackage.
`joinGroupFromBranch` accepts that Welcome against Bob's original state.
After the original group commits a ReInit to `expected-reinit`,
`joinGroupFromReinit` accepts the same ordinary Welcome and returns an
active state for `unrelated`.

**Impact and prerequisites:** a party able to deliver a Welcome for the
recipient's published KeyPackage can substitute a different group during
an application-requested branch or ReInit, provided the Welcome's signer
and credentials pass the application's authentication policy. The proof
uses the already known Alice as signer. A delivery service with no
accepted signing key cannot fabricate that Welcome by itself. An
application that independently verifies the resumption relationship can
prevent the substitution; these API wrappers do not enforce it.

**Fix:** pass an explicit expected resumption mode into `joinGroup` from
each wrapper. Require the appropriate PSK, old group ID, and epoch before
accepting the join or wiping the init key. Keep ordinary `joinGroup`
available for ordinary invitations. Add negative tests for missing PSKs,
application-usage PSKs, the wrong resumption usage, and a normal Welcome
with an unrelated group ID. The branch and ReInit contracts are described
in [RFC 9420 sections 11.2 and 11.3][rfc-resumption].

## F2. Medium: an invalid PSK proposal blocks normal sends and commits

Locations:

- `src/client-state.ts:1472`: `validateProposalOnReceipt`.
- `src/create-commit.ts:313`: `filterPendingProposals`.
- `src/psk-index.ts:25`: nonce-length check during PSK accumulation.
- `src/client-state.ts:141`: application-send gate.

Receipt validation handles Add, Update, Remove, and ExternalInit, but
does not validate PSK nonce length. A correctly authenticated PSK proposal
with an empty nonce is stored. The commit-time filter calls the same
incomplete validator and keeps the proposal. `accumulatePskSecret` then
rejects it, so `createCommit` cannot produce a new state. Application
messages also fail because the pending set is nonempty.

**Reproduction:** Bob creates a public PSK proposal with a zero-byte
nonce. Alice processes it with the default incoming-message policy and
stores one pending proposal. Alice's next commit throws
`PreSharedKeyID pskNonce length does not match KDF.Nh`, even with a PSK
lookup that supplies the referenced secret. Her next application send
throws `Cannot send application message with unapplied proposals`.

**Impact and prerequisites:** a group member can prevent a recipient's
ordinary commit and send operations with one signed proposal. An
authorized external sender can also propose PSKs. Repeating operations
against the returned state does not recover it. Explicitly discarding
the proposal or accepting a valid commit that excludes it can recover;
this is not permanent destruction of the group or key material.

This is a remaining instance of the pending-proposal problem in the
September audit. Add/Update validation and the pending-count bound do
not cover it.

**Fix:** reject structurally invalid PSKs on receipt, including wrong
nonce length and disallowed resumption usage for the current epoch.
Retain the commit-time checks and make the pending filter exclude
proposals that cannot be committed. Test that invalid signed proposals
leave the pending set unchanged and do not disable application sends.
Keep PSK availability decisions at the layer that has the PSK lookup.

## F3. Medium: malformed leaf encryption keys enter the ratchet tree

Locations:

- `src/client-state.ts:557`: `validateLeafNodeCommon`.
- `src/client-state.ts:678`: `validateKeyPackage`.
- `src/update-path.ts:190`: import of recipients' encryption keys.

Leaf validation verifies signatures, credentials, capabilities, and key
uniqueness, but never checks that the leaf's HPKE public key is valid
for the ciphersuite. `validateKeyPackage` imports `initKey` only.
A signed KeyPackage can therefore carry a valid init key and an invalid
leaf encryption key.

**Reproduction:** Mallory signs a KeyPackage whose X25519 leaf encryption
key is the single byte `01`, while keeping a valid init key. Alice adds
it to an existing Alice/Bob group. Alice produces the commit and Welcome;
Bob accepts the commit; the Welcome join also accepts the malformed
tree. Bob's next empty commit tries to encrypt an UpdatePath to that
leaf and throws
`CryptoError: DeserializeError: Invalid public key for the ciphersuite`.

**Impact and prerequisites:** an applicant whose credential and Add are
approved can insert a broken key using a valid signature. This leaves
honest members unable to complete path commits whose copath resolution
includes that leaf. Removing the bad leaf can recover the group. The
failure is delayed until a later operation, making it harder for the
application to associate with the admitted KeyPackage. No confidentiality
break was demonstrated.

**Fix:** validate encryption keys during common leaf validation, covering
Add, Update, Commit, and Welcome trees. Check algorithm-specific encoding
and validity, including any low-order restrictions import alone does not
enforce. Reject peer-invalid material as `ValidationError` before it
enters state. Add tests for malformed lengths and invalid points across
the supported providers. Key validity is required by
[RFC 9420 sections 5.1.1 and 7.3][rfc-keys].

## Dependency observations

`npm audit --omit=dev --json` returned zero advisories. The full audit
returned five affected package entries: three high and two moderate.
These are development dependencies, not five independent defects in the
published library.

The lockfile contains `wrangler@4.149.0`,
`miniflare@5.20261006.1-alpha`, and `undici@7.29.1`.
The Undici version is affected by GHSA-xjj6-f33q-929c, a high-severity
unhandled-error denial of service on excessive response content
encodings; the 7.x fix is 7.30.1. Two other Undici advisories concern
EventSource memory usage and integrity algorithm parsing. The upstream
[Undici advisory][undici-advisory] documents the fixed versions.
Exploitability through this repository's specific tooling commands was
not reproduced.

The other chain is the already documented `markdown-toc`, `gray-matter`,
and `toml` tooling. Current registry results differ from the older count
in AGENTS.md. No dependency was changed. Do not apply the audit's suggested
Wrangler downgrade blindly; resolve a compatible fixed toolchain, update
the lockfile with npm, and verify with `npm ci`.

## Validation results

- Structural checks: passed all five `test:checks` scripts.
- Typechecks: root, scripts, and Worker configurations all passed.
- Library build and `check:package`: passed, including CJS/ESM consumers.
- Both demo builds: passed. Neither output contains `window.state=`.
- Targeted proof: all three findings reproduced successfully.
- `npm run test:fast`: 42,027 assertions, 42,026 passed, one failed.
  The failure is `test/example/how-to-use.ts:44`, expecting one `h2`
  but finding zero. Running that file alone reproduced the failure.
  This is a pre-existing presentation-test failure, not a security finding.
- Secret-file exclusions: `.env.local`, `.dev.vars.production`, and
  `private.pem` are ignored; `.env.example` is not. The tracked-ignored
  files currently reported are `PROMPT.md` and `ralph_claude.sh`.
- A targeted pattern scan of application/library/workflow files found
  no matching private-key blocks or common AWS/GitHub/Stripe token shapes.
  This was not a complete secret scan of Git history.

Commands ran on Node 26.11.1 and npm 12.2.0 with the existing
`node_modules`, not a fresh `npm ci`. Installed tooling differs from the
lockfile: for example, installed Undici is 7.29.0. Advisory results above
refer to the lockfile; test/build results refer to the installed tools.
The full ciphersuite matrix, browser suite, Swift interoperability suite,
and a deployed Worker penetration test were not run. The attachment
review was targeted; it did not rederive the cryptographic construction
or replace the separate attachment audit and cross-implementation tests.

## Reproduce the library findings

From the repository root, using the installed esbuild:

```sh
./node_modules/.bin/esbuild docs/audit-repros/2026-10-24.mjs \
  --bundle --platform=node --format=esm \
  --outfile=/tmp/webcrypto-audit-2026-10-24.mjs
node /tmp/webcrypto-audit-2026-10-24.mjs
```

The [standalone proof](docs/audit-repros/2026-10-24.mjs) creates ephemeral
groups locally. It does not contact a server, publish messages, or change
library code. Its assertions intentionally confirm the defects, so it
should fail after the corresponding fixes; it is not registered as a
normal regression suite.
