# Own-Generated Test Vectors for SEAL and Attachment CEK Derivation

This directory contains regression-test vectors generated by the implementation
covering two domains: SEAL-RO-v1 epoch digest tree (snap_id 0x0003) and MLS
attachment Content Encryption Key (CEK) derivation via draft-ietf-mls-extensions
and draft-sullivan-mls-attachments.

## Format

### epoch-tree.json

SEAL epoch digest tree vector containing:

- `name`: Identifier for the vector
- `description`: Human-readable description
- `configuration`: Cryptographic configuration
- `cek_hex`: Content Encryption Key (32 bytes, fixed 0xAA for reproducibility)
- `salt_hex`: Fixed salt (32 bytes, fixed 0x04 for reproducibility)
- `object_id_hex`: Object identifier (fixed "own-vector" ASCII)
- `plaintext_length`: Length of plaintext (65536 + 100 bytes)
- `commitment_hex`: Commitment derived from CEK and parameters (32 bytes)
- `snapshot_hex`: Epoch digest tree root snapshot (32 bytes)
- `first_64_bytes_hex`: First 64 bytes of sealed object (salt + commitment)
- `object_sha256_hex`: SHA-256 digest of complete sealed object bytes

### keys.json

Attachment CEK derivation vector containing:

- `epoch_secret_hex`: Epoch secret (32 bytes, fixed 0x42 for reproducibility)
- `application_export_secret_hex`: Derived application_export_secret from
  epoch secret via draft-ietf-mls-extensions (32 bytes)
- `component_id`: Component ID for attachment_encryption (0xF001, decimal 61441)
- `object_id_hex`: Object identifier for CEK derivation (fixed
  "own-vector" ASCII)
- `component_secret_hex`: Component secret derived via exporter tree walk from
  application_export_secret (32 bytes)
- `cek_hex`: Content Encryption Key derived for the object (32 bytes)

## Epoch-Tree Vector

### Cryptographic Configuration

- **Protocol ID**: SEAL-RO-v1
- **AEAD**: AES-256-GCM (aead_id 2)
- **KDF**: HKDF-SHA-256 (kdf_id 1)
- **Nonce Mode**: Derived (0x01)
- **Epoch Length**: 10 (2^10 = 1024 segments per epoch)
- **Snapshot ID**: 0x0003 (epoch digest tree)
- **Segment Max**: 65536 bytes

## Plaintext

Counter bytes from 0 to 65635 modulo 256, producing one full segment
plus one final segment:
- Segment 0: bytes 0-65535
- Segment 1: bytes 65536-65635 (final segment, 100 bytes)

## References

Normative references for vectors in this directory:

- draft-sullivan-seal-concrete-00: SEAL algorithm and named instantiations
  (epoch-tree.json)
- draft-sullivan-cfrg-raae-02: RA-AE application-layer encryption
  (epoch-tree.json)
- draft-ietf-mls-extensions-09: Safe Extensions framework including
  SafeExportSecret and ComponentOperationLabel (keys.json)
- draft-sullivan-mls-attachments: MLS attachment content encryption and
  references (keys.json)

The component ID `0xF001` used in keys.json is a provisional private-use value
pending IANA assignment (see `src/attachment/keys.ts:11-24`). When the IANA
value is assigned, regenerating these vectors with a new component ID will
change every derived key, so this value is wire-breaking and held
provisionally.

Note that `snap_id 0x0003` (epoch digest tree in epoch-tree.json) has a
conformance note in `src/attachment/schedule.ts`, which records that
this pairing is the conformant one, and
`docs/design-plans/2026-08-19-random-access-attachments.md`. The epoch tree
and attachment CEK derivation are locked only by our own frozen vectors
because swift-raae does not implement 0x0003.

## Generation

Vectors are generated deterministically by
`scripts/generate-seal-own-vectors.ts` with fixed inputs. For
epoch-tree.json the CEK, salt, objectId and plaintext are fixed; for
keys.json the epoch secret is fixed at 0x42. Re-running the generator
must produce bit-identical bytes, so any mismatch signals an
unintended implementation change.

There is no TypeScript runner in devDependencies, so the generator is
not invoked directly. `scripts/check-vector-determinism.mjs` bundles it
with esbuild and runs the bundle, and that check runs on every
`npm run test:node`, before the unit tests. It generates into a
temporary directory and compares against the committed vectors rather
than regenerating over them, so a failure never leaves the committed
files modified.

To re-freeze deliberately, run the generator the same way the check
does, passing the target directory as its one argument.
Any divergence causes the test run to fail.
