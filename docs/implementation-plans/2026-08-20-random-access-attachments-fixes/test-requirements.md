# Test Requirements: Random-Access Attachment Fixes

Scope: `phase_01.md` through `phase_06.md` in this directory. Every
acceptance criterion those phases declare maps below to either an
automated test or a documented human verification. Ids are the scoped
form `random-access-attachments-fixes.ACn.m`; the phase files abbreviate
them to `ACn.m` and this document does the same after the first mention
in each section.

Criteria in the parent slug `random-access-attachments` are referenced
by their full scoped id when they come up, because two of the phases
correct or extend them and confusing the two slugs is easy.

Written: 2026-08-20, from the phase files as written rather than from
any summary of them.

## Conventions this document assumes

1. Every automated test is a `@substrate-system/tapzero` file under
   `test/`, registered by an `import './...js'` line in `test/unit.ts`.
   A file that is not registered there does not run, fails nothing and
   reports nothing; adding the import is part of the task that adds the
   file.
2. New attachment test files are registered **inside the attachment
   block**, which runs from line 18 (`import './attachment/seal-core.js'`)
   to line 28 (`import './attachment/vectors-all.js'`), and always
   **before** the `// Example app tests` marker at line 30. That
   ordering is load-bearing: `npm run test:browser` aborts partway
   through the example suite on a pre-existing fake-IndexedDB conflict
   in `test/example/member-store.ts`, so anything imported after the
   marker never runs in a browser. Registration position, not the
   browser run's exit code, is what this document treats as evidence of
   browser coverage.
3. The two structural gates are
   `scripts/check-attachment-invariants.mjs` and
   `scripts/check-vector-determinism.mjs`. `npm run test:checks` runs
   both and nothing else; `npm run test:node` chains it ahead of the
   full suite. `npm run test:unit` bundles `test/unit.ts` with esbuild
   and runs it under node, and runs neither script. In CI the gates are
   their own `checks` job running `npm run test:checks`, so a violation
   fails the build on every push -- the test matrix jobs run
   `test:unit` and `test:matrix` and would not catch one. Where a
   criterion is discharged by a gate rather than by an assertion, the
   verification command is `npm run test:node` (or `npm run
   test:checks` for the gate alone) and nothing weaker.
4. Test types used below:
   - unit: single module, pure or near-pure, no cross-layer wiring.
   - integration: several attachment modules wired together in one
     process (still a tapzero file registered in `test/unit.ts`).
   - e2e: crosses a process boundary into another implementation (the
     Swift CLI), run by a separate npm script.
   - gate: a node script in `test:checks`, chained ahead of the tests
     in `test:node` and run on its own as the CI `checks` job. Not a
     test, but it fails both the standard test command and the build,
     and this document treats it as coverage only where the criterion
     is itself structural.
5. Every rejection is asserted with the subsystem's error idiom: the
   call inside `try`, `t.ok(false, ...)` immediately after it, and
   `t.ok(err instanceof AttachmentError, ...)` in the `catch`. There is
   one error type on purpose (`src/attachment/AGENTS.md`), so no
   assertion may test for anything more specific.
6. Test vectors are data, not tests. `test_vectors/seal/core/` and
   `test_vectors/seal/engine/` are vendored and never edited.
   `test_vectors/seal/own/` is generated by
   `scripts/generate-seal-own-vectors.ts`. Phase 5 turns the
   "byte-identical on re-run" property from a convention into a
   command; see AC5.2.
7. Every new structural gate must be observed failing once,
   deliberately, and then restored. A guard nobody has seen fail is not
   a guard. Each gate below names its negative control.
8. Prose has no test runner. AC6 is entirely documentation accuracy and
   is human-verified by reading the cited source lines. No automated
   test is invented for a documentation claim anywhere in this
   document; where a mechanical aid exists it is named as an aid and
   not as coverage.

## Automated coverage

### random-access-attachments-fixes.AC1: Padding gap authentication

Implemented in phase 1. All AC1 tests live in one new file,
`test/attachment/padding.ts`, registered per convention 2. The
predicate under test is `isZeroRegion` in `src/attachment/layout.ts`;
its two consumers are `openObject` (`object.ts`, at the length check)
and the gap-skipping loop in `reader.ts`.

**AC1.1** -- an object whose padding gap contains a non-zero byte is
rejected by `decryptAttachmentStream` before any plaintext is emitted.

- Type: integration.
- File: `test/attachment/padding.ts`.
- Assertions: seal an object, flip one byte at an index in
  `[l.headerSize, l.firstBlockOffset)`, feed the bytes to
  `decryptAttachmentStream` as a `ReadableStream`, and assert the stream
  errors with `AttachmentError`. Collect every emitted chunk in an array
  and assert in the `catch` that the array is empty. The
  emitted-nothing half is the part that makes this AC1.1 rather than a
  duplicate of AC1.2, so it is not optional.
- Chunk-boundary cases: repeat with at least two chunk sizes (one small
  enough that the gap spans many chunks, for example 1024) and at least
  two flip positions, one near the start of the gap and one near the
  end, so the flipped byte lands away from a chunk start. Reuse the
  `chunked(bytes, size)` helper the existing suite already has at
  `test/attachment/stream-helpers.ts:5`. `test/attachment/streams.ts`
  imports it from there; it has never been declared in that file.

**AC1.2** -- the same object is rejected by `openObject`.

- Type: integration.
- File: `test/attachment/padding.ts`.
- Assertions: `openObject` over the same tampered bytes rejects with
  `AttachmentError`. Compute the gap offsets by calling `layout()` with
  the parameters the seal used; do not hard-code 64 KiB, or the test
  stops following a parameter change.

**AC1.3** -- an unmodified object still verifies under both read paths
and the wire format is unchanged.

- Type: integration.
- File: `test/attachment/padding.ts`.
- Assertions: the untampered object opens under `openObject` and
  decrypts under `decryptAttachmentStream`, both returning plaintext
  byte-identical to the input. This is the regression guard proving the
  new check did not break the happy path.
- Format-stability gate, outside the test file:
  `git diff --exit-code test_vectors/seal/own/` must be empty after the
  phase. A non-empty diff means the change was not read-side only.

**AC1.4** -- rejection holds across a sweep of plaintext sizes that vary
the gap length.

- Type: integration (the sweep) plus unit (the empty-gap boundary).
- File: `test/attachment/padding.ts`.
- Sweep: at minimum a sub-segment object, an object of exactly
  `segmentMax`, a few-segment object comparable to the existing
  131,089-byte fixtures, and an object spanning several epochs so `nEp`
  and therefore `headerSize` grow. For each size, compute the layout,
  flip a gap byte, and assert both `openObject` and
  `decryptAttachmentStream` reject. Derive every offset from `layout()`.
- Empty-gap boundary, stated honestly: the gap is empty only when
  `headerSize` is an exact multiple of `segmentMax`, first reached at
  nSeg 1362 for nh 32, which is about 85 MiB of plaintext, and at
  nSeg 6546 for nh 64, about 409 MiB. Phase 1 rules those out on peak
  allocation under `test:browser`, not on wall-clock cost. The boundary
  is therefore covered where it lives, in the predicate, by the
  `from === to` and `from > to` unit cases on `isZeroRegion`. Phase 1
  declares that substitution part of AC1.4 rather than a shortfall
  against it, and this document records it the same way. The test file
  must state that reachable empty-gap sizes exist and are too large to
  seal here, not that no reachable size produces an empty gap.
- Predicate unit cases (same file): all-zero sub-range returns `true`; a
  single non-zero byte inside the range returns `false`; a non-zero byte
  immediately outside the range on either side does not affect the
  result; `from === to` and `from > to` both return `true`.

**Scope limit, deliberate.** `range.ts` never fetches the gap, so a
range read structurally cannot check it. AC1 applies to the two
whole-object read paths only. Phase 1 task 5 records this in
`src/attachment/AGENTS.md`; no test asserts anything about `range.ts`
here, and adding one would be asserting on an absence.

### random-access-attachments-fixes.AC2: Derived-key zeroization

Implemented in phase 2. All AC2 behavioural tests live in one new file,
`test/attachment/cek-wipe.ts`, registered per convention 2.

**The control assertion comes first, and is itself required.** The
tests instrument `cs.kdf.expand` on the **ciphersuite** (not on a
`SealCrypto` bundle, which the writer wrapper rebuilds internally) and
record every expand output. The CEK is the 17th expand, because
`safeExportSecret` walks 16 tree levels first, and a length assertion
cannot distinguish it from a tree node since both are 32 octets on
SHA-256 suites. So one shared helper derives the CEK independently, and
asserts `recorded[16]` deep-equals it, before any wipe assertion runs.
Without that control every other assertion in this section could pass
against a tree node. Treat a failure of the control as a signal that
`keys.ts` changed its call count, not as a flaky test.

Why the existing suite could not have caught any of this: the
zeroization assertion in `assertScheduleWiped`
(`test/attachment/streams.ts:43`) names exactly `payloadKey`, `snapKey`
and `nonceBase` -- the literal list is at
`test/attachment/streams.ts:52` -- which is the definition of
`wipeSealState`. The CEK is not in that list and never could be.

**AC2.1** -- `encryptAttachmentForGroup` zeroizes its derived CEK on the
success path and on the throw path.

- Type: integration.
- File: `test/attachment/cek-wipe.ts`.
- Assertions: after the wrapper resolves, every byte of the recorded CEK
  is zero; and with `cs.hpke.encryptAead` instrumented to reject, the
  wrapper rejects and the CEK is still zero.

**AC2.2** -- the reader wrapper zeroizes on every ending the machinery
can reach.

- Type: integration.
- File: `test/attachment/cek-wipe.ts`.
- Five endings, each its own test: normal close (read to completion);
  error (tampered object, stream errors mid-read); cancel (`cancel()`
  the reader partway); pre-header failure (input truncated below
  `headerSize`, so the stream errors before `ctx` exists); and
  construction throw (a ref with a bad `version`, so
  `decryptAttachmentStream` throws synchronously and no stream is ever
  built). The `version` field specifically: an out-of-range `objectId`
  throws inside `attachmentCek` before a CEK exists, leaving nothing to
  assert against.
- Two-flag regression test: cancel while the header is still being
  verified, then drive the stream to its error path, and assert both
  that the CEK is zeroed and that the `SealState` was wiped. A
  single-latch implementation passes the five endings and fails this
  one. The cancel must be landed deterministically by gating on the
  instrumented `kdf.expand`, not by racing the four `sealKdf` awaits in
  `deriveSchedule`. A test that only sometimes enters the window it
  exists for is worse than no test.

**AC2.3** -- the range wrapper zeroizes on close, error, cancel,
construction throw, and seek-then-abandon followed by `close()`.

- Type: integration.
- File: `test/attachment/cek-wipe.ts`.
- Five shapes, each its own test, matching AC2.2's list with
  seek-then-abandon in place of the pre-header case. For
  seek-then-abandon, where no stream is ever constructed, assert both
  halves: the CEK is live before `close()` and zero after. Asserting
  only the second half would pass against an implementation that wiped
  too early.
- Single-use contract: one further test asserting that a second
  `decrypt()` on an `AttachmentRangeRead` whose stream has already ended
  rejects with `AttachmentError`. This pins a real behaviour change that
  a caller would otherwise discover in production.
- Explicitly **not** tested: `decrypt()`-then-abandon. `range.ts` is
  exempt from that shape because `new ReadableStream` auto-pulls once at
  `highWaterMark: 1` and its `pull` runs unconditionally to the wipe, so
  the "live before close" half cannot hold and a test written to beat
  the auto-pull would be racing a timer. Phase 2's Architecture section
  is the reference; do not add the test.

**AC2.4** -- deleting any one wipe fails a test.

This is a meta-criterion about the quality of the AC2.1-AC2.3 tests, not
a behaviour with a test of its own, and it cannot be discharged by an
assertion inside the suite: a test that asserts "some other test would
fail if the code changed" is a test of a counterfactual.

- Automated part (gate, partial): phase 2 task 4 extends
  `scripts/check-attachment-invariants.mjs` with a presence check that
  `writer.ts` contains a `.fill(0)` and that `reader.ts` and `range.ts`
  each contain `ownedCek`. This catches wholesale removal of a wipe. It
  cannot prove a wipe is reachable, and the script must carry a comment
  saying so and pointing at `test/attachment/cek-wipe.ts`. Negative
  control: remove the `ownedCek` argument from the `reader.ts` wrapper,
  confirm non-zero exit, restore.
- Human part: H1 below. One documented exemption, at the CEK wipe in
  `range.ts` `pull`'s catch (around `range.ts:281-283`), which is
  unreachable by construction: `pull()` cannot observe a null
  `decrypted`, and its only other throw sources run after `ctx = null`.
  No test can kill that wipe. It stays for symmetry with the
  surrounding `wipeSealState` call, and no test may be manufactured that
  appears to cover it.

**AC2.5** -- the residual gaps and the single-use contract are stated
where a caller will see them.

Documentation. Human-verified by inspection; see H2. There is no
automated coverage and none is proposed: the criterion is about a reader
of `AttachmentRangeRead` and `src/attachment/AGENTS.md` encountering the
disclosure, which no assertion observes.

**Residual gaps: recorded, not tested.** Phase 2 deliberately does not
close these, and this document does not map them to tests that do not
exist:

1. A range read constructed and abandoned without calling `close()`
   still leaks its CEK. Nothing at this layer can prevent it; `close()`
   is the offered remedy and calling it is the caller's choice.
2. A reader stream constructed and then abandoned without being read or
   cancelled leaks its CEK, its `SealState`, **and one buffered segment
   of decrypted plaintext**. `decryptAttachmentStream` returns a bare
   `ReadableStream` with nowhere to hang a disposal hook; adding one is
   a public API change outside this phase. The buffered plaintext is the
   part a reader of that note will care about most and must not be
   omitted from the disclosure.

Both are AC2.5 disclosure obligations, verified by H2. Neither is a test
failure, and a future reader should not read their absence from the
suite as an oversight.

### random-access-attachments-fixes.AC3: Pluggable RNG and corrections

Implemented in phase 3.

**AC3.1** -- `sealObject` draws its salt from the supplied bundle's
`rng`.

- Type: unit.
- File: `test/attachment/object.ts` (existing file, extended).
- Assertions: build a bundle whose `rng.randomBytes` is a counting stub
  returning a known pattern; seal with no `opts.salt`; assert the salt
  in the produced header is the stub's output **and** that the stub was
  called, so the test cannot pass by coincidence. Then assert
  `opts.salt` still wins and the stub is not called when a salt is
  supplied.
- Explicitly not asserted: that `globalThis.crypto.getRandomValues` was
  not called. That is wiring rather than behaviour, and AC3.2 enforces
  it structurally instead.
- Vector stability: `git diff --exit-code test_vectors/seal/own/` must
  be empty, since the generators pass an explicit salt.

**AC3.2** -- no file under `src/attachment/` calls `getRandomValues`.

- Type: gate. `scripts/check-attachment-invariants.mjs`.
- Check: match both `globalThis.crypto.getRandomValues` and bare
  `crypto.getRandomValues`, scoped to `getRandomValues` specifically.
  Matching `globalThis.crypto` alone would fail on
  `crypto.ts:106`'s legitimate `subtle` use on its first run.
- Negative control: add a `getRandomValues` call in
  `src/attachment/object.ts`, confirm non-zero exit, remove it.

**AC3.3** -- the `keys.ts` forbidden-import list includes
`reference.ts`, and a deliberate violation trips it.

- Type: gate. `scripts/check-attachment-invariants.mjs`.
- Negative control: add an import of `reference.ts` to `keys.ts` **plus
  a use of it**, confirm non-zero exit, revert. The use is required: the
  check bundles and inspects `metafile.inputs`, so an unused import is
  tree-shaken away and the control would silently prove nothing.

**AC3.4** -- the unreachable safe-integer branch in `reader.ts` is
removed with no behaviour change.

- Type: no new test by design; dead-code removal guarded by existing
  coverage of the two surviving clauses.
- Corrected 2026-08-22 (US-020 of the audit remediation). This section
  originally cited `test/attachment/reader-header.ts:220-247` as
  asserting that `verifyHeader` rejects `Number.MAX_SAFE_INTEGER + 1`.
  It does not. Those cases are the `REJECTED_LENGTHS` table at
  `test/attachment/reader-header.ts:246`, driven through `layout()` at
  `:253`, not through `verifyHeader`. The guard is redundant across
  `verifyHeader`, `parsePrefix` and `layout`, and deleting either outer
  copy leaves the suite green, so `layout()` is the only layer at which
  it can be pinned. The comment block at
  `test/attachment/reader-header.ts:222-245` now records that.
- The safe-integer clause and the `MAX_SEGMENTS` ceiling are separate
  guards. `MAX_SAFE_INTEGER + 1` never reaches the ceiling, because
  `nSeg` is not computed for it. The ceiling has its own tests, added by
  US-020: `layout rejects a plaintextLength one octet past MAX_SEGMENTS`
  at `test/attachment/reader-header.ts:309`, an accept-the-ceiling
  control below it, and the entry-point case
  `verifyHeader rejects a plaintextLength past MAX_SEGMENTS` at
  `test/attachment/reader-header.ts:357`, which pins `AttachmentError`
  at `:376`. Both fail when `if (nSeg > MAX_SEGMENTS) throw` is removed.
- `plaintextLength <= 0` is covered by the `zero` and `negative` rows of
  `REJECTED_LENGTHS`, through `layout()` for the same redundancy
  reason.
- Do not touch the `bigint` bounds check inside
  `decryptAttachmentStream`. It operates on a differently typed `ref`
  and is not redundant. Confirm which site you are editing by reading
  the declared type of `ref` at each.

### random-access-attachments-fixes.AC4: Verification parity

Implemented in phase 4. All AC4 tests live in one new file,
`test/attachment/parity.ts`, registered per convention 2. Every variant
is built once and driven through both read paths from the same bytes;
two sets of fixtures is how the paths drift apart in the first place.
The two entry points take different ref shapes (`openObject` wants
`{ snapshot, plaintextLength:number }`, the streaming path wants an
`AttachmentRef` with `plaintextLength:bigint`), so both refs are built
from one source of truth in a helper.

**AC4.1** -- the two paths agree on the verdict for any mutation of a
sealed object's bytes.

- Type: integration (differential).
- File: `test/attachment/parity.ts`.
- Assertions: seal one fixture spanning several segments and at least
  two epochs; for a deterministic list of byte offsets, flip a byte and
  run the result through both paths; assert both accept or both reject.
  Never assert which verdict: the property is agreement, not
  correctness, and pinning the verdict makes the test brittle to
  legitimate change. On disagreement, fail with a message naming the
  offset and which path accepted.
- Offsets, all derived from `layout()` and never hard-coded: inside the
  salt, the commitment, the stored snapshot, an epoch head, the metadata
  leaf run, the padding gap, a segment ciphertext, and a segment tag.
  No random sweep: a test that fails only on some runs teaches people to
  re-run it.
- Scope limit: this test mutates **bytes only**. It does not vary the
  ref, so it cannot detect ref-shaped divergence, including the
  `version` asymmetry that remains after phase 4. That is why AC4.1 is
  scoped to mutation agreement and why the asymmetries are documented
  rather than asserted.
- Falsification (required, and the choice matters): weaken one of
  `openObject`'s constant-time comparisons (the leaf check or the
  epoch-head check) so `openObject` accepts offsets the streaming path
  still rejects, confirm the test reports disagreement and names the
  offset, then restore. Do **not** falsify by removing the
  `bytes.length !== l.totalSize` guard: the sweep never changes the
  object's length, so that removal changes no verdict and the test
  stays green. Do not rely on reverting phase 1's padding check either,
  since phase 4 is independent of phase 1 and may run first.
- Documentation half: the enumeration of deliberate asymmetries in
  `src/attachment/AGENTS.md` is human-verified, part of H5's checklist.

**AC4.2** -- all four attack shapes are rejected by both read paths.

- Type: integration.
- File: `test/attachment/parity.ts`.
- Variants, each asserted `AttachmentError` from `openObject` and from
  `decryptAttachmentStream`: drop the final segment; swap segments 0 and
  1; substitute a segment with the same-index segment from an object
  sealed under a different CEK; alter one byte inside a segment
  ciphertext.
- "No plaintext emitted" may be asserted on the streaming side **only**
  for shapes detectable from the header. For a mid-object alteration the
  streaming reader legitimately emits earlier segments first; that is
  deliberate asymmetry 3, not a defect.
- Prior state: both paths are believed to reject all four already, and
  this task turns a by-hand observation into a standing test. If any
  shape turns out not to be rejected, that is a live vulnerability, not
  a coverage gap: stop and report it rather than writing a fix.

**AC4.3** -- `openObject` rejects an out-of-range `objectId`; malformed
`plaintextLength` is a parity assertion over existing behaviour.

- Type: integration.
- File: `test/attachment/parity.ts`.
- New behaviour: `openObject` rejects a zero-length `objectId` and an
  `objectId` longer than 255 octets, matching the bounds `sealObject`
  and `validateAttachmentRef` already enforce. These are the only
  genuinely new assertions in AC4.
- **Parity over existing behaviour, not new coverage:** the
  non-positive and non-safe-integer `plaintextLength` cases already pass
  before the change, because `openObject` calls `layout()` and `layout()`
  throws for them. They are here to document parity. Phase 4 explicitly
  forbids adding a second `plaintextLength` check in `openObject`, and
  the test file must carry a comment saying these cases pass before the
  change, so a later reader does not mistake them for coverage of the
  new guard.
- For each case, assert the streaming path rejects the equivalent input
  too, so the test documents the parity rather than only the new
  behaviour.

**AC4.4** -- both paths reject a truncated object and an object with
trailing bytes.

- Type: integration.
- File: `test/attachment/parity.ts`.
- **Parity over existing behaviour, not new coverage.** Both paths
  already reject both shapes. The streaming half is already covered at
  `test/attachment/streams.ts:2117` (extra bytes) and `:1736`
  (truncation), and those tests stay. What this criterion adds is the
  `openObject` half and, more importantly, one shared fixture driving
  both, so the next divergence fails loudly. No source change is
  expected; if one turns out to be needed, that is a finding to report
  before fixing.

### random-access-attachments-fixes.AC5: Interop and determinism

Implemented in phase 5.

**AC5.1** -- the harness pins, as an assertion, that vendored swift-raae
cannot accept snap_id 0x0003, and pins the specific rejection reason.
CONDITIONAL.

- Type: e2e (crosses into a Swift process), gated on a toolchain.
- Command: `npm run test:interop` (`scripts/run-interop.mjs` bundles and
  runs `scripts/interop-seal.ts`).
- Assertions in the new case: send `op: 'schedule'` with `protocol_id`
  `PROTOCOL_RO` and `payload_info.snap_id` 0x0003, the remaining fields
  matching what the library emits; assert the response carries an
  `error` field (a success here is a failure of the test); and assert
  the error text names `unsupportedSnapID`. The last assertion is the
  whole point: a bare "it failed" check would still pass if swift-raae
  began rejecting for a different reason, including rejecting our tuple
  as non-conformant, which is the one outcome we would most want to hear
  about. Print a line saying what was pinned and that a failure here
  means upstream capability changed and real round-trip coverage should
  now be added.
- This case is not marked a skip. It is a passing assertion about a
  known limitation, not an absent test.
- Falsification (required): change the expected substring to something
  swift-raae would not emit, confirm the harness fails, change it back.
- **Conditionality, explicit.** This criterion requires a Swift
  toolchain, and the vendored sources it reasons about live under
  `interop/seal-cli/.build/checkouts/swift-raae/`, which is gitignored
  and absent from a fresh clone until `swift build -c debug` restores
  it. When `swift` is not on PATH the harness prints
  `SKIP: swift toolchain not found` and exits 0, so a machine without
  Swift stays green. **A SKIP is not a pass for AC5.1.** If the run that
  is being relied on prints the SKIP line, AC5.1 is unverified and the
  missing toolchain is a follow-up item, not a green result. The
  authoritative run is the CI `interop` job on `macos-14`, or a local
  run on a machine with the toolchain. Confirming the distinction is
  human verification item H3.

**AC5.2** -- re-running the vector generator produces byte-identical
output, checked by a command wired into the standard test run.

- Type: gate. `scripts/check-vector-determinism.mjs`, in
  `test:checks` alongside `scripts/check-attachment-invariants.mjs`,
  so it runs before the `test:node` test run and as the CI `checks`
  job.
- Mechanics: the generator gains an output-directory argument
  (`process.argv[2]`, defaulting to the current hard-coded path). The
  check creates a temporary directory outside the repository tree,
  bundles and runs the generator into it the way
  `scripts/run-interop.mjs` handles `scripts/interop-seal.ts`, and
  compares every produced file byte for byte against its counterpart in
  `test_vectors/seal/own/`. It must fail, not pass, on a produced file
  with no committed counterpart or a committed file the generator no
  longer produces: comparing only the intersection would miss a vector
  being dropped. It must clean up the temporary directory on both the
  pass and the fail path, and name the first differing file on failure.
- The check must never write into `test_vectors/seal/own/`. A check that
  mutates the thing it is checking will one day be interrupted halfway
  and leave the repository in a state nobody ordered.
- Negative control: edit one byte of a committed vector, re-run, confirm
  non-zero exit and that the message names that file, restore with
  `git checkout`, confirm a clean tree.
- Note on the parent document: the "byte-identical on re-run" property
  appears in the parent `test-requirements.md` as convention item 5. It
  is stated there as a convention, not as a gate that "must hold on
  every standard test run" -- that phrasing does not appear in the file.
  Phase 5 makes it a gate for the first time.

**AC5.3** -- the parent criterion `random-access-attachments.AC5.2` is
reworded to match what the harness actually verifies.

Documentation. Human-verified by inspection; see H4. Two concrete
falsehoods must go: the promised range-read leg, which is skipped, and
the `snap_id 3` configuration line, when the harness runs 0x0000 and
0x0001 and 0x0003 is the value swift-raae rejects. The criterion is

### random-access-attachments-fixes.AC6: Documentation accuracy

Implemented in phase 6. **This criterion is entirely documentation
accuracy, across all eight items. There is no test runner for prose,
and no automated test is proposed for any of them.** Every item is
verified by a human opening the source file and line that settles the
claim and reading it. Correcting a document from a summary of the code
is the failure mode this whole phase exists to fix, and a fabricated
automated test would be a second instance of it.

Two mechanical checks are available. Neither verifies that a document is
*correct*; each rules out one specific way of being wrong.

1. **Grep, for AC6.2 only.** After the phase:

   ```sh
   grep -rn "invalidProfileTuple" \
       src/ docs/design-plans/ docs/test-plans/ AGENTS.md \
       interop/seal-cli/README.md test_vectors/ scripts/
   ```

   Expected: no matches. The exclusions are deliberate and must stay
   excluded: the vendored checkout under `interop/seal-cli/.build/`
   legitimately defines the error and must not be edited, and this
   plan's own phase files under `docs/implementation-plans/` quote the
   wrong name in order to say it is wrong, so a repository-wide grep
   would match them and never go green. Note that the range-read skip
   comment in `scripts/interop-seal.ts` misattributes by citing
   `KeySchedule.swift:152-158` and does **not** contain the string, so
   the grep does not cover it; phase 5 task 1 is what corrects it.

2. **Output equivalence, for the whole phase.** No documentation edit
   should change the output of `npm run test:node` or
   `npm run test:interop`. Both are run at the end of phase 6 for
   exactly this reason: a change in either means an edit strayed into a
   source or vector file. A pass proves only that nothing was broken; it
   says nothing about whether any corrected sentence is true.

The per-item checklist, each item paired with the artifact that settles
it, is H5 below.

## Human verification

### H1: AC2.4, deleting any wipe fails a test

Criterion: `random-access-attachments-fixes.AC2.4`.

**Why this is not automated.** The criterion is a claim about the tests
themselves, not about the code: it asserts that no wipe in the subsystem
is unguarded. An assertion inside the suite cannot establish it, because
it would have to observe the suite's behaviour under a mutation of the
source, which is a mutation-testing tool the repository does not have.
The invariants script's presence check catches wholesale removal only,
and its own comment must say so.

**Approach.** Once per wipe site, by hand: delete the wipe, run
`npm run test:node`, confirm at least one test in
`test/attachment/cek-wipe.ts` fails, restore. Sites are the `finally` in
`encryptAttachmentForGroup`, the CEK branch of `doWipe` in `reader.ts`,
the wrapper's `catch` in `reader.ts`, `wipeCek` at each of the four
`range.ts` sites and in `close()`, and the wrapper's `catch` in
`range.ts`.

**One exemption, documented rather than papered over.** The CEK wipe in
`range.ts` `pull`'s catch (around `range.ts:281-283`) is unreachable by
construction: `pull()` cannot observe a null `decrypted` because
`start()` either assigns it or errors the stream, and `pull`'s only
other throw sources are `enqueue` and `close`, which run after
`ctx = null`. No test can kill it. Keep it for symmetry with the
adjacent `wipeSealState` call, record the exemption, and do not
manufacture a test that appears to cover it.

**Evidence to record** in the phase 2 task log: one line per wipe site
naming the test that failed, and the exemption restated.

### H2: AC2.5, the residual gaps are disclosed where a caller sees them

Criterion: `random-access-attachments-fixes.AC2.5`.

**Why this is not automated.** The criterion is about a reader
encountering a disclosure at the moment they would need it. A grep for
the words would pass against a sentence that says the wrong thing, and
the substance is whether the note is accurate and findable, which only
reading it establishes.

**Approach.** Read and confirm all four claims are present and correct:

1. On the `AttachmentRangeRead` interface: a range read abandoned
   without calling `close()` still leaks, and nothing at this layer can
   prevent it.
2. On the same interface: the read is single-use once any stream has
   ended or `close()` has been called, so a second `decrypt()` will
   fail. Cross-check against the single-use test under AC2.3, which is
   the executable half of this claim.

   AMENDED DURING EXECUTION. This holds only when the read owns the
   CEK, which means only when it was opened via
   `openAttachmentRangeForGroup`, the path that passes

   asked for the unconditional claim. AC2.5's own standard is whether
   the note is accurate and findable, and the qualified note is the
   accurate one, so the shipped text is right and this line is the

   Confirm the buffered plaintext is named. That is the part a reader
   will care about most and the part most likely to be dropped in
   summary.
4. In `src/attachment/AGENTS.md` or at the wipe site: why the wipe is
   not conditioned on `ctx`, and why a `cancel()` landing mid-schedule
